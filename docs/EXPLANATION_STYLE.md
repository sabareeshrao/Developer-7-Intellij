# Explanation Card Style

The explanation card should sound like a clear coding walkthrough, not a textbook.

## Required

- Talk about the exact thing visible on screen.
- Explain the reason while the learner can still see the code or control.
- Connect new work to something already built when that connection matters.
- Keep wording natural; openings and transitions should vary.
- Mention a future dependency only when it helps orientation.
- Prefer concrete GeoOps examples over generic definitions.

## Forbidden

- Reusing the same full sentence in two explanations.
- Mechanical templates such as beginning every step with "Now we are..." or ending every step with "Next we will...".
- Long dictionary-style definitions detached from the action.
- Inventing future architecture before its set.
- Creating a second explanation UI; the master global explanation card is authoritative.

The build script performs a sentence-level duplicate check for narration.
